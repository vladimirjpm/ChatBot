Детальный разбор по разделам

A. Бизнес-задача / Product Mindset
6
Реализовано
Два режима (interview / assistant), scope документов (shared / private), multilingual, streaming UX.
Что отсутствует
Аутентификация, история между сессиями, аналитика, rate limiting, onboarding.
B. Архитектура
7
Реализовано
Core / Infrastructure / Api — Onion. DI через интерфейсы. Провайдер-агностичный IEmbeddingGenerator. Комментарии с дорожной картой (M.Extensions.AI).
⚠️ Критично
AddScoped<IChatService> + Dictionary<Guid,SessionState> в instance — новый экземпляр на каждый запрос, история теряется fixed. CORS AllowAnyOrigin fixed. Нет UseExceptionHandler. PostgreSQL / Redis только в конфиге.
C. Frontend
6
Реализовано
Кастомные хуки (useChat, useDocuments, useDocumentUpload). SSE через ReadableStream + AbortController. Discriminated union типы. i18n из shared JSON.
Отсутствует
Error Boundary. React Query / SWR. Глобальный стейт. Suspense. E2E тесты.
D. Backend API
6
Реализовано
Minimal API. SSE с flush. CancellationToken везде. Validation входных данных. OpenAPI. Health checks разделены live / ready.
Отсутствует
UseExceptionHandler. Rate limiting. Auth middleware. Ограничение размера файла. Валидация MIME-типа.
E. AI / LLM
8
Реализовано
RAG pipeline. Два режима grounding. RAG-контекст НЕ пишется в историю (anti-context-pollution). Провайдер-switching (OpenAI / Ollama). Локализованные промпты в JSON-конфиге.
Отсутствует
Tool Calling / Function Calling. Structured Output. Retry при timeout. Token counting. Eval framework. Semantic caching.
F. Базы данных
4
Реализовано
Qdrant — gRPC, фильтрация по scope/sessionId, graceful при отсутствии коллекции. QdrantClient Singleton (thread-safe).
⚠️ Критично
PostgreSQL и Redis — есть в docker-compose и appsettings, но нигде не используются в коде. Выглядит как незавершённость.

Вопросы, которые задаст интервьюер

Вероятные вопросы
«Что будет, если перезапустить сервер во время разговора?»
Сессии хранятся в памяти (InMemorySessionStore). При перезапуске вся история теряется — пользователь начинает заново. Фикс — Redis: заменить InMemorySessionStore на Redis-реализацию. Интерфейс ISessionStore уже есть в Core, ChatService его не знает — это swap без изменения логики.
«Как ты масштабируешь до 1000 одновременных пользователей?»
Сейчас in-memory сессии не дают запустить несколько инстансов — все запросы должны попадать в один pod. С Redis сессиями можно поднять N реплик за load balancer. Qdrant и OpenAI — уже внешние сервисы. SSE-стримы stateless на уровне запроса, горизонтальное масштабирование работает сразу после выноса сессий.
«Как защищён shared upload от злоупотреблений?»
Никак — сейчас любой может сделать POST на /api/documents/upload с scope=shared и засорить общую базу знаний. Фикс — auth middleware, проверяющий X-Api-Key header перед эндпоинтом. Это пункт 5 из топ-10 улучшений.
«Покажи CI/CD pipeline»
CI: GitHub Actions запускает dotnet restore → build → test на каждый push и PR в main (.github/workflows/ci.yml). CD: Railway автодеплоит бэкенд из main, Vercel — фронтенд. Сломанный тест блокирует разработчика до мержа, но не блокирует Railway — это следующий шаг.
«Почему PostgreSQL в compose, но не в коде?»
Заскаффолдён как инфраструктура для будущего хранения истории чатов (EF Core + миграции). Сейчас сессии in-memory и персистить их не нужно. PostgreSQL — плановое хранилище для ChatSessions, это улучшение №7. Redis — для session state, улучшение №3.
«Как ты мониторишь LLM-latency в продакшне?»
Сейчас только /health и /health/live — метрик нет. План: OpenTelemetry — AddOpenTelemetry().WithTracing().WithMetrics(), histogram вокруг SK chat-вызова, экспорт в Prometheus/Grafana. Это улучшение №4.
«Как ты управляешь context window при длинном диалоге?»
Semantic Kernel держит всю ChatHistory в памяти на время сессии. При очень длинных разговорах упрёмся в лимит контекста модели. Митигация — sliding window или суммаризация: хранить последние N сообщений и добавлять rolling summary. Не реализовано — текущие демо-сессии достаточно короткие.
